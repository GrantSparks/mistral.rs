import { Tabs, TabItem } from '@astrojs/starlight/components';

Speculative decoding drafts several tokens per step using a separate assistant or the model's built-in prediction head. The target model verifies the drafts in parallel before emitting accepted tokens. Configure it through the MTP (Multi-Token Prediction) API.

:::caution
Speculative decoding requires [paged attention](/guides/perf/paged-attention/), which is enabled by default on CUDA.
:::

<Tabs>
<TabItem label="CLI">

```bash
mistralrs run -m google/gemma-4-E4B-it --quant 8 \
  --mtp-model google/gemma-4-E4B-it-assistant \
  --mtp-n-predict 6
```

`--mtp-model` accepts a Hugging Face id or a local path. The same flags work with `mistralrs serve`. See [run](/reference/cli/run/) and [serve](/reference/cli/serve/) flag references.

</TabItem>
<TabItem label="Python">

```python
from mistralrs import Runner, Which

runner = Runner(
    which=Which.MultimodalPlain(model_id="google/gemma-4-E4B-it"),
    in_situ_quant="8",
    mtp_model="google/gemma-4-E4B-it-assistant",
    mtp_n_predict=6,
)
```

Gemma 4 loads via `Which.MultimodalPlain` and uses a separate assistant checkpoint.

</TabItem>
<TabItem label="Rust">

```rust
let model = mistralrs::ModelBuilder::new("google/gemma-4-E4B-it")
    .with_mtp_model("google/gemma-4-E4B-it-assistant", Some(6))
    .build()
    .await?;
```

You can also pass `MtpConfig::new("google/gemma-4-E4B-it-assistant", Some(6))` to `with_mtp_config`. Use `MtpConfig::builtin(None)` for a built-in head with automatic draft depth. These methods are available on the text, multimodal, and auto-detecting model builders.

</TabItem>
</Tabs>

`--mtp-n-predict N` fixes the number of draft tokens per step. Without it, the engine tunes depth using draft acceptance, step time, and batch size, periodically trying other depths as the workload changes. Built-in Qwen heads choose among 2, 3, 4, and 6 drafts. Gemma 4 uses the same candidates, capped by `num_assistant_tokens` in the assistant's `generation_config.json` (6 if absent). DFlash uses the policy described below.

## Supported models

| Mode | Target models | Assistant model | Status |
|---|---|---|---|
| MTP | Gemma 4 | Gemma 4 assistant checkpoints (`--mtp-model`) | Supported with paged attention |
| MTP | Qwen3.5, Qwen3.8 | Built into the checkpoint (`--mtp`) | Supported with paged attention |
| MTP | Qwen3.8-Flash-Next | Built into the checkpoint (`--mtp`) | Safetensors/UQFF with paged attention |
| DFlash / DFlash 2 | Qwen3.5, Qwen3.8 | DFlash draft checkpoints (`--mtp-model`) | Supported with paged attention |

## Qwen3.5 / Qwen3.8

Qwen3.5 and Qwen3.8 checkpoints ship a multi-token prediction head (`mtp.*` weights) sharing the target's embeddings and `lm_head`. Pass `--mtp` to load it; no separate assistant model is needed:

```bash
mistralrs serve -m Qwen/Qwen3.8-27B --quant 4 --mtp
```

The head adds one attention layer's paged KV cache. Safetensors and UQFF checkpoints must contain the `mtp.*` weights; GGUF loading does not support built-in MTP.

Multi-token verification can use different quantized matrix and recurrent kernels from ordinary decoding. Log probabilities and greedy token choices can differ, so token-for-token equivalence is not guaranteed.

Built-in Qwen MTP recomputes cached prompt prefixes, which can increase time to first token for repeated prompts. This restriction does not apply to DFlash.

Qwen3.8-Flash-Next uses the same built-in-head flags:

```bash
mistralrs serve -m Qwen/Qwen3.8-Flash-Next --isq q4k --mtp
```

Flash-Next supports only its built-in head. External assistants and DFlash are unsupported. See [model-family notes](/guides/models/model-family-notes/#qwen38-flash-next) for memory requirements.

## DFlash and DFlash 2 (Qwen3.5 / Qwen3.8)

[DFlash](https://arxiv.org/abs/2602.06036) drafters are small block-diffusion models that propose a
whole block of tokens in one pass, conditioned on hidden states tapped from the target's
intermediate layers. They reach much higher acceptance than the built-in single-token MTP head.
Pass a DFlash checkpoint (a HF id or local path) as `--mtp-model`; mistral.rs detects DFlash vs
DFlash 2 from the checkpoint's `architectures` and loads the path selector and dynamic convolutions
when present:

```bash
mistralrs serve -m Qwen/Qwen3.8-27B --quant 4 \
  --mtp-model incoai/Qwen3.8-27B-DFlash2
```

`--mtp-draft-sampling` defaults to `auto`. A DFlash 2 checkpoint uses probabilistic drafting when
its CUDA candidate selector is supported, while DFlash 1 and unsupported devices use greedy
drafting. Pass `--mtp-draft-sampling greedy` to force greedy drafting. Passing `probabilistic`
requires a supported DFlash 2 selector and fails during loading when that path is unavailable.

The maximum automatic draft depth is `min(block_size - 1, 7)`. During serving, mistral.rs may use a
shallower depth so the recurrent checkpoint layout fits the configured sequence capacity while
preserving memory for the requested paged KV cache. Pass `--mtp-n-predict` to request a fixed depth
instead. Automatic CUDA serving also adapts the active depth to live load: up to 8 live DFlash
contexts use the full reserved depth, while larger loads use up to 3 drafts. Set
`MISTRALRS_DFLASH_ADAPTIVE=0` (or `false`) to tune depth from measured throughput instead.
That tuner also runs when adaptation by live context count is unavailable. It chooses among
3, 5, and 7 drafts, capped by the reserved depth. The drafter's projection
weights are requantized to the target's in-situ quantization type at load (override with the
`MISTRALRS_DFLASH_ISQ` environment variable, e.g. `q6k` or `none` for bf16).

Acceptance is strongly content-dependent: [incoai/Qwen3.8-27B-DFlash2](https://huggingface.co/incoai/Qwen3.8-27B-DFlash2)
accepts ~7 of 7 drafts on math/code and much less on thinking-mode reasoning traces, which are out
of its training distribution.

## Gemma 4

Gemma 4 assistant checkpoints are MTP drafters for Gemma 4 target models. See the [`google/gemma-4-E4B-it-assistant`](https://huggingface.co/google/gemma-4-E4B-it-assistant) model card for the upstream checkpoint. A downloaded checkout works too:

```bash
mistralrs run -m google/gemma-4-E4B-it --quant 8 \
  --mtp-model ./gemma-4-E4B-it-assistant \
  --mtp-n-predict 6
```

Non-paged KV-cache MTP is intentionally disabled for now, which is why paged attention is required (see the note at the top).

The target and assistant configs must match where the implementation requires it, including vocabulary size and target hidden size. Mismatches fail at load, before generation starts.

## Notes

Throughput gain depends on how many proposed tokens the target accepts and on the cost of the target verification pass.

MTP supports batched generation and constrained decoding.

MTP is configured at launch time only (CLI flags, `Runner(...)`, or the model builder). There is no per-request HTTP field to toggle it; load the server with the assistant attached and every request uses it.

## Request observations

When inference observations are enabled (`MISTRALRS_INFERENCE_OBSERVATIONS`), the existing
`Usage.engine_observation` on single-choice causal requests can include an optional
`speculative` block. The Rust SDK exports `EngineObservation` and `SpeculativeObservation`.
Observation-disabled requests omit engine observations. Ordinary observations omit the
`speculative` field and retain their existing JSON representation. Multiple-choice requests
and genuinely unsupported paths do not publish an engine observation, even if an error
later reduces the number of live choices to one.

The counters describe actual source events:

| Field | Scope and boundary |
| --- | --- |
| `verification_steps` | Acceptance passes entered, including a final pass interrupted by a stop, cancellation or error. This is not a count of completed target forwards. |
| `proposed_draft_tokens` | Whole proposal rows entering those passes; excludes anchors and target continuations. Proposals staged without entering an acceptance pass are excluded. |
| `accepted_draft_tokens` | Inspected target-comparison decisions that accept a draft, before decoding and append. A later append failure can leave this larger than `committed_draft_tokens`. |
| `committed_output_tokens` | Actual output tokens appended to the sequence during the whole request, including ordinary tokens preceding speculative entry, anchors, target continuations, EOS, stop tokens and nonvisible output. |
| `committed_draft_tokens` | Accepted drafts actually appended after speculative observation begins. Rejected drafts and uninspected proposals after a stop or length limit are excluded. |
| `measurement_complete` | The observed counters cover the terminal committed output boundary. This does not attest later speculative state or cache commit, successful delivery to a disconnected client, numerical equivalence, or complete inspection of every proposal. |
| `terminal_reason` | Known output boundary or interruption: `eos`, `stop_token`, `stop_string`, `max_output_tokens`, `model_length`, `tool_calls`, `canceled` or `error`. An unfinished snapshot can have no reason. |

Counters and timestamps are updated before terminal Usage publication. The final verification
step is included even though the driver receives its verification result afterward. EOS,
hidden stop bytes and the final allowed output token count when appended; the remaining
proposal tail does not count as committed output. Available canceled/error snapshots are
partial (`measurement_complete: false`). A closed sender can drop the response; the engine
does not manufacture a final Usage response in that case.

Use the validity flags inside the block before interpreting legacy fields:

| Flag | Meaning when true |
| --- | --- |
| `cache_fields_valid` | Existing optional cache facts came from direct prefix lookup, restore or final reuse events. Individual `None` fields remain unknown. The reused prefix is recorded after source replay/clip decisions, not inferred from a candidate hit. |
| `prefill_geometry_valid` | Successful prompt forwards supplied exact sequence query ranges for the existing `prefill_chunk_count` and `prefill_chunk_max_tokens`. Unsupported or ambiguous geometry stays unknown. |
| `prefill_host_forward_sec_valid` | Every contributing prompt host-forward interval belonged to a single sequence. Any shared dispatch makes the request total permanently unknown. |
| `token_markers_valid` | First/last token timestamps use the sequence clock immediately after actual append. If ordinary sampler-boundary timestamps preceded speculative entry, the combined markers are unknown even though committed token counts remain known. |

`raw_prompt_sec_valid` and `raw_completion_sec_valid` are currently false for speculative
requests: the old phase totals are not exact speculative request timing. Missing validity
flags deserialize as false. Do not turn unknown timing or cache facts into zero durations,
cache misses or exact throughput.

`proposal_host_dispatch_sec` is the sum of actual single-sequence `speculative_propose`
call-to-return host intervals. It excludes planning, cache lookup, target-hidden preparation,
`speculative_prepare_propose` and subsequent staging. It does not synchronize the GPU or
measure device completion. Shared batches, failed calls or unavailable intervals permanently
invalidate the total. `proposal_host_dispatch_unavailable` distinguishes `no_proposal_dispatch`,
`shared_batch`, `proposal_dispatch_failed` and `interval_unavailable`.

`verification_host_dispatch_sec` is currently unknown, with
`verification_host_dispatch_unavailable: "target_forward_interval_unavailable"`. The target
forward and token acceptance cross existing dispatch boundaries, so the engine does not
reuse a batch interval or divide shared time between requests to populate this field.
